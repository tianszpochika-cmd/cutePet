## 1. 结论

**产品方向有合理基础，功能范围较完整；核心业务规则与功能链尚未达到可全量冻结的程度。建议本轮“有条件通过方向与范围，暂不通过核心链路规则冻结”。**

合理之处：以宠物档案建立持续记录价值，家庭共享与提醒形成协作场景；资讯、探索、用品各有职责；一期排除交易与商业化，避免引入订单、支付、售后整套体系；内容审核、举报、降级、跨端回跳已经进入设计。

主要问题：部分链条仍以“用户依次访问多个页面”代替“完成一项任务并获得结果”；跨文档存在角色、状态、字段和入口冲突。尤其是 L2 提醒、L9 家庭共享，以及活动和 UGC 供给链，开发者若直接按当前文档实施，仍需自行作出重要产品决策。

本轮保留已经确认的六项范围决策，包括探索全量、家庭共享、UGC 和移动端全量。不建议以本报告为依据自行删减一期模块。建议调整规则补齐与验证顺序。

## 3. 产品合理性：成立的部分与未验证的假设

### 3.1 四个模块能组成产品，但不能直接视为已成立的增长循环

“管理→资讯→探索→用品”有场景关联，但任务间的转化理由仍然偏弱。例如完成一次驱虫记录，并不自然意味着用户要查看体重曲线或继续刷资讯；查看附近医院，也不意味着会发表评价。

现有 L2 把“看曲线→刷资讯”串成必然步骤，而疫苗、驱虫、复诊等记录不一定产生新的体重点。更合理的主任务结束点是“本次照护已记录、家人已知晓、下次安排明确”，相关资讯应作为可选后续动作。

证据：`01-需求文档/需求全景-功能清单.md:17–26,118`；`02-设计文档/交互设计.md:37–45`。

### 3.2 “日常留存”与现有行为频率尚未建立证据关系

当前依赖疫苗、驱虫、体检、复诊等提醒，日常喂食等记录在二期。现有材料未验证这些任务对目标用户的发生频率，也未证明完成任务后会继续消费内容。不能因此断言留存一定失败，但暂不能把周活和内容停留增长当成已经成立的产品机制。

愿景中的业务目标、用户特征仍待填，用户调研和竞品分析也是模板。建议先明确首发核心人群与首要任务，并把跨模块转化列为待验证假设。无需为提高打开频次擅自加入签到、积分或日常记录。

证据：`00-项目概述/项目愿景与目标.md:9–25`；`03-研究资料/用户调研.md:5–24`；`01-需求文档/需求全景-功能清单.md:50`。

### 3.3 当前是多模块首发版本，验证和运营成本需要单独管理

四端、UGC、家庭、路线、活动、领养和内容导购均进一期，属于已确认范围。真正的负担不仅是页面开发，还包括首发供给、资料更新、认证、审核、投诉和活动履约通知。

冷启动计划已提出供给和审核编制，但明确是建议值、待负责人确认。应保留范围，分链验收和分批放量；首发城市、供给负责人、审核排班和预算需要成为运营准入条件。

证据：`01-需求文档/PRD-总纲.md:15–40`；`03-研究资料/冷启动运营计划.md:3–26`。

## 4. 重点发现与可执行修订条件

“高优先级”指会影响主流程、权限或需求验收，需要在对应模块定稿前解决；“中优先级”指会影响产品效果、跨端一致性或运营可执行性。本表不把文档问题等同于已经发生的运行故障。

### R01 · 高：L2 的正式需求与本地演示验收边界没有统一

**证据**：`01-需求文档/需求-宠物管理.md:28–34` 明确移动推送是一期核心；`需求-多端需求矩阵.md:45–49` 称其为生命线。`05-技术文档/开发任务规划.md:48,232,316` 已选择响应式 H5，使用站内消息与 Web Notification 模拟 L2，厂商推送留接口；同时 `:12,24–28` 又要求需求范围内全量功能可测。

**问题与影响**：本地目标允许模拟是合理的，但这些验收不能证明用户离开产品后仍能被提醒召回。这里的问题是两套交付承诺没有建立对应关系，并非断言 H5 无法实现任何推送。官网仍以“下载 App”为主要入口，也未与当前形态对齐。

**修订建议**：建立“本地流程可测 / 真实通道可用 / 正式产品验收”三列能力清单；明确离站触达适用条件、失败反馈、用户关闭通知后的产品承诺和责任任务；官网 CTA 与实际可用端一致。若正式能力仍保留原承诺，应保留未完成项，不能仅由“已知限制”自动抵销。

**关闭条件**：验收分别覆盖在线、后台或关闭页面、拒绝通知、断网恢复和家人已完成等场景；每项注明实际支持范围与证据，模拟结果不计为真实触达通过。

### R02 · 高：重复提醒已有状态机，但一次照护任务没有完整闭环

**证据**：`02-设计文档/功能设计.md:36–43` 已写“完成→自动排下次”；`功能设计-宠物管理.md:55–61` 定义三天过期、家人可处理；`交互设计.md:40–43` 要求完成时进入记录表单；移动 UX `:146` 只写完成后记时间线。

**问题与影响**：缺的是下一次从原计划日还是实际完成日计算、过期后是否继续排期、补录历史记录是否完成当前任务、家人同时处理时如何合并，以及完成记录失败时提醒能否先变成完成。当前把周期计划与某次执行混在同一“提醒”概念中，完成后重回已启用也难以直接定义历史完成率。

**修订建议**：在业务概念上区分“提醒计划”和“本次待办”；定义任务完成与健康记录的关系、重复完成规则、过期/补录/关闭/恢复规则、排期基准，以及处理人和通知接收人的关系。资讯推荐作为任务完成后的可选动作。

**关闭条件**：同一待办由两位家人几乎同时提交，只形成一次有效完成；下一期待办唯一；失败和重试不会重复记健康记录；三天过期后仍有明确可执行路径；提前、按时、延迟完成的下次日期都有例子。

### R03 · 高：宠物所有者与家庭创建者被混为同一角色

**证据**：`01-需求文档/需求-宠物管理.md:45` 指档案创建者所有；`需求-账号与用户体系.md:46–55` 定义家庭与成员。`02-设计文档/功能设计-账号与个人中心.md:31–38` 却把“邀请/移除成员、解散”放在“宠物所有者”列并标为“=创建者”。`数据设计.md:23–25` 又定义家庭与宠物 N—N 共享。

**问题与影响**：甲创建家庭、乙带自己的宠物加入时，乙是宠物所有者但不是家庭创建者。现有表不能清楚回答乙能否解散家庭、甲能否删除乙的宠物，以及只读/可管理权限究竟对整个家庭还是某只宠物生效。移动 UX `:134` 的“可管理=全功能”进一步扩大歧义。

**修订建议**：拆开家庭管理权、宠物所有权、共享访问权、记录作者四个概念。逐项明确删除、归档、导出、分享、改权限、邀请、解散等动作。说明一只宠物允许共享给一个还是多个家庭，使文字与关系图一致；邀请默认权限和调整入口也要确定。

**关闭条件**：以“甲建家庭、乙拥有宠物、丙只读、丁可管理”为矩阵逐项验收；不得因拥有一只共享宠物就取得全家庭管理权。

### R04 · 高：家庭退出、注销与离线同步交叉场景没有落地规则

**证据**：`02-设计文档/功能设计-账号与个人中心.md:41,79` 要求注销前转移/归档或移出家庭；移动 UX `:198` 使用“家庭创建者且有共享宠物”的阻断条件，与功能分册不完全一致。多端需求 `:48` 要求联网自动同步；宠物功能设计 `:37` 为后写覆盖；账号功能设计 `:91` 为下一次鉴权失效。转移所有权只有提示，未见独立流程与接收规则。

**问题与影响**：用户被引导到未定义的转移操作；个人作为宠物所有者但不是家庭创建者时，注销检查可能不同。成员离线录入后被移除，再联网时自动同步应拒绝、保留还是丢弃，也没有约定。恢复软删档案的权限、入口和提醒处理同样未闭环。

**修订建议**：补家庭解散/退出/移除、档案移出/转移/删除/恢复、账号冷静期的事件影响表。明确转移双方确认及失败回退，或统一现有可执行替代路径。离线待同步数据在提交时重新判权，定义失败说明和安全清理；已合法导出的静态副本不承诺远程收回。

**关闭条件**：可执行完成创建者与非创建者的注销；离线旧成员不能重新写入已失权档案；换号/登出不串用待同步数据；恢复宠物后历史、共享和提醒状态符合明确规则。

### R05 · 高：活动只有提交报名，组织者和后续状态未闭合

**证据**：`01-需求文档/需求-宠物探索.md:37–43` 定义认证机构、普通用户发布、报名信息提供；`02-设计文档/功能设计-宠物探索.md:60–64` 有名额但无名额规则；移动 UX `:111–114` 增加成功凭证。`功能设计-管理端.md:39,76–77` 仅提供内部运营的发布审核和报名导出。

**问题与影响**：认证机构的申请、授予/撤销身份、发布入口、查看自己报名者的入口和数据范围未定义。报名缺少重复提交、截止、满员、本人取消、活动取消或改期、再次查看报名结果等规则。“无需审核”只解决是否人工批准，不能替代这些状态。凭证码也未定义用途。

**修订建议**：补“组织者身份→发布→审核/直发→报名→我的报名/组织者名单→取消或变更通知→结束→数据清理”全链。领养与普通活动分别定义动作；活动是否限额、凭证是否仅供查询均需明确，不必因此增加支付、复杂核销或商家后台。

**关闭条件**：最后一个名额并发报名结果明确；重复点击不占双份名额；组织者只看到自己活动的数据；改期/取消能通知受影响者；普通活动与领养发布审核规则分别可验证。

### R06 · 高：首次投稿入口被隐藏，作者清单缺少完整创作路径

**证据**：`01-需求文档/需求-宠物资讯.md:42,58` 规定个人中心进入创作、登录用户默认可投稿；`02-设计文档/信息架构.md:87` 提供创作入口；移动 UX `:185` 却写“创作[无投稿隐藏]”，资讯 Feed `:67–70` 也未明确替代投稿按钮。`功能设计-宠物用品.md:45–49` 允许作者创建清单，而移动 UX `:169–176` 只有文章编辑器；管理端队列 `:7–9` 未明确清单类型。

**问题与影响**：按逐屏规格实现，新作者可能没有首次创作入口；“要先有投稿才显示投稿入口”形成循环依赖。清单消费页有了，作者生产和审核如何进入仍不清楚。

**修订建议**：无投稿用户仍显示创作入口，用空态引导首次发布；补文章/清单的创作类型、商品选择和排序、草稿、审核与结果回跳。清单是否作为文章子类型应明确并映射到审核队列。

**关闭条件**：全新账号仅从首页和“我的”出发，即可完成首次文章与作者清单投稿、驳回修改、审核发布及消费者查看。

### R07 · 高：健康记录的日期校验会与未来提醒日期冲突

**证据**：`02-设计文档/功能设计-宠物管理.md:28–36` 同时规定疫苗/驱虫的“下次提醒日期”、用药起止日期以及“日期不得晚于今天”；移动 UX `:138` 原样采用“日期>今天→字段红字”。

**问题与影响**：若按当前统一规则实现，今天记录一次接种并设置未来提醒会被拦截，持续用药的结束日期也可能被错误拒绝。此处是字段级规则冲突，不是断言现有代码已出错。

**修订建议**：按发生日期、计划日期、用药起止日期分别校验；明确未来结束日期是否支持、起止关系、缺失历史日期与补录规则。体重“较七日前”也应定义当天无数据时使用哪个基准。

**关闭条件**：今天的健康事件能设置未来提醒；未来发生的已完成事件按规则拦截；用药日期组合与无七日前体重点场景都有确定结果。

### R08 · 高：先审后发没有覆盖发布后的修改与重新发布

**证据**：`01-需求文档/需求-宠物资讯.md:44–45` 与 `02-设计文档/功能设计-宠物资讯.md:47–62` 定义首次审核与下架，但未定义已发布稿件的修改流程；`功能设计-管理端.md:22,58` 允许编辑已存在文章和任意文章。

**问题与影响**：若修改直接影响在线内容，原有审核结论不再对应当前内容；若修改后立即撤掉旧稿，则会影响正常阅读和既有分享。文章、路线、活动时间地点和商品清单关联变更都需要规则，不能只复用首次提交状态。

**修订建议**：选择明确的修改策略：禁止作者编辑并提供更正流程，或区分线上版本与待审修改版；规定哪些变化需复审、审核期间旧版是否可见、并发编辑和撤回如何处理。活动关键变更还需衔接 R05 的报名者通知。

**关闭条件**：已发布内容修改后，消费者看到的版本与有效审核结论一致；未审修改不因原稿已通过而自动上线；被下架对象也不能通过普通保存绕过复核。

### R09 · 中：L7 分享拉新混用了公开内容与私有档案

**证据**：`01-需求文档/需求全景-功能清单.md:123` 以时间线分享进入落地页；宠物功能设计 `:65–70` 只定义健康摘要静态图片；账号功能设计 `:33,58` 保持档案仅本人和家庭可见。移动页面架构 `:152` 又将摘要分享列为对应详情深链。

**问题与影响**：公开文章/路线深链、静态健康摘要图片、家庭私有时间线是三种不同的访问方式。当前未明确时间线究竟分享什么、游客访问什么，以及静态图片如何承接注册归因。没有证据可以认定当前已经公开泄露档案，但实现者可能自行补出不一致的行为。

**修订建议**：建立分享对象表，写明公开范围、分享载体、游客落点、登录后回跳和下架/失效结果。健康摘要可继续保持静态快照；若无需公开时间线，就将 L7 的表达与现有能力对齐。基础内容分享与二期邀请裂变工具要分开。

**关闭条件**：游客不能靠分享链接进入实时私有档案；静态摘要与实时详情的界限清晰；公开内容分享后被下架，访问结果一致；一期拉新指标有实际可采集事件支持。

### R10 · 中：内容导购的可信度要求没有完整传到表单与治理

**证据**：`01-需求文档/需求-宠物用品.md:13,34` 排除处方粮等商品并强制标注“编辑部测试/资料整理”；`02-设计文档/功能设计-宠物用品.md:15` 仍列“处方”标签，评测定义 `:39–41` 仅写文章加关联商品；移动编辑器 `:172` 未明确内容来源字段。

**问题与影响**：需求已定的品类边界与设计标签矛盾；可信度强制字段未落实到提交和展示条件。资讯“科学、可信”的定位也主要依赖安全过滤与免责声明，专业事实核查责任没有展开。后者是产品信任机制缺口，不是本次作出的医疗或法律判断。

**修订建议**：统一商品允许范围和标签；把评测来源作为评测类型的必填项，确定消费者展示位置与审核检查项。对健康类内容明确来源、复核责任和更正路径，避免仅以内容安全审核代替事实可信度审核。

**关闭条件**：禁止品类不会从普通录入或批量导入进入商品库；缺失来源标识的评测不能发布；消费者能识别测试与资料整理内容，并找到纠错入口。

### R11 · 中：链路有指标名称，但还没有可用于判断产品成功的口径

**证据**：`01-需求文档/需求全景-功能清单.md:115–126` 给出建档率、周活、裂变系数、内容飞轮转速等名称；管理端需求 `:39–40` 将口径和埋点交给设计，功能设计-管理端 `:99–109` 仍标草案；交互设计仅零散列出向导 PV、导航点击等。愿景与用户调研尚无验证结果。

**问题与影响**：无法区分提醒创建/触发/送达/打开/完成，也无法明确一次家庭协作算一位还是两位活跃用户。导航点击只能证明发起导航，不能证明到店；纯内容导购没有订单，不宜用购买转化解释效果。多个模块数据都上涨也不能直接证明同一用户完成跨模块转化。

**修订建议**：为每条链定义起点、终点、用户或家庭粒度、去重口径、观察窗、事件及属性、分母与排除项。把“导航发起”与“到店”分开，把导购价值落在评测阅读、商品收藏和回访等一期可观察行为。成功阈值结合试用结果由负责人确认。

**关闭条件**：给定一组包含重复点击、家庭多人处理、测试账号、跨日记录的样例，各端和运营对同一指标算出一致结果；有指标结果支持假设复评，而不只记录页面访问量。

## 6. 其他需要同步修订的事项

1. **健康摘要的场景适配**：B6 面向就医/寄养，但选择项以“近 30 天记录”为主，应明确历史过敏、当前用药等信息是否单独展示，避免旧的长期信息只因记录日期早而不可选。证据：宠物需求 `:36–38`、宠物功能设计 `:66`。
2. **年龄分支的边界**：需求按“年满 14 周岁”，移动 UX `:29–30` 却只询问出生年份。临界年龄无法单凭年份判断；应选择能准确处理边界的最少信息。监护人撤回入口虽已写入设置，还需明确监护人如何独立核验与访问；开发任务 `T1.2` 已规定撤回后账号受限，不能误报为完全没有撤回后效果。
3. **非违规驳回与处罚**：资讯功能设计 `:52` 将累计三次驳回直接暂停投稿七天，未区分排版、材料不足与违规，也未写统计窗口和恢复后计数。应分离内容质量修改与违规处置，避免种子作者因普通修改被限权。
4. **评价规则漂移**：探索需求 `:30` 为“全五星且正文少于十字”等复审条件；探索功能设计 `:39` 写成“全五星+无文+图重复”。新号“先审后计入评分”与任务规划“新号评价先审”的可见性也需统一，明确公开展示和计分是两个状态。
5. **隐私告知矛盾**：移动 UX `:163` 加入家庭告知“对方也可见你的互动”，账号功能设计 `:39` 保留对方收藏/投稿私有。需逐项说明共享什么，避免宽泛告知改变原有隐私边界。
6. **封禁后的申诉身份**：移动 UX `:204` 已有封禁页申诉按钮，不能说没有入口；但任务规划 U1–U7 写封禁后鉴权拒绝，需明确受限身份可执行哪些申诉/查结果动作，避免按钮有了而流程不可用。
7. **文档状态与口径维护**：根 README 仍写阶段一，AGENTS 写进入阶段二/三；里程碑仍有设计评审未通过项。移动页面架构首部写 47 屏、清单实际到 57；功能链 B2/B3 的曲线编号和 E4 的范围引用也有错误。应统一这些状态，但不把编号修正当成业务缺口已修复。

## 7. 建议补齐后的核心链路

### 照护与家庭协作

```text
建立宠物档案
→ 设置提醒计划（明确真实可用渠道）
→ 产生本次待办
→ 有权限的家人收到或查看待办
→ 任一可管理成员记录本次照护
→ 确认保存成功，并完成该次待办
→ 其他家人看到处理人及结果
→ 按已确定规则生成下一次待办
→ 可选查看相关内容
```

### 活动

```text
发布者身份确认 → 发布/审核 → 展示
→ 用户告知同意 → 报名并校验截止/名额/重复
→ 用户可查报名，组织者可查自身名单
→ 取消/变更时状态更新并通知
→ 活动结束 → 报名信息按既定期限清理
```

### UGC

```text
新用户可见创作入口 → 选择文章/清单 → 草稿
→ 提交 → 审核 → 发布 → 互动反馈
→ 修改走明确的修订规则 → 再审核/更正
→ 下架/申诉/恢复时消费者、作者、运营状态一致
```

## 8. 修订顺序与复审出口

| 顺序 | 工作 | 产出与出口 | 建议责任角色 |
|---|---|---|---|
| 1 | 明确 R01 的产品与本地交付边界 | 能力验收表，统一当前端形态及官网入口 | 产品负责人 + 开发负责人 |
| 2 | 补 R02/R03/R04/R07 | 提醒执行规则、角色权限矩阵、退出事件表、字段校验表；包含异常用例 | 产品/功能设计负责人 |
| 3 | 补 R05/R06/R08 | 活动组织者闭环、首次创作与清单、修改审核状态及对应页面入口 | 产品 + 运营 |
| 4 | 补 R09/R10/R11 及其他矛盾 | 分享对象表、可信度字段、指标字典与规则一致性校验 | 产品 + 内容运营 |
| 5 | 回填全景、分模块需求、设计、任务和验收 | 每项修改可追溯，不只改一份文档；负责人复审关闭问题 | 文档维护者 + 负责人 |

复审至少走查以下情景：

- 新用户首次投稿，完成一篇文章和一份商品清单。
- 同一提醒被两位家人并发处理，记录保存失败后重试，下一次仍只有一条有效待办。
- 今天的健康记录关联未来提醒，延期完成后排期结果确定。
- 家庭创建者与宠物所有者不是同一个人，分别编辑、移出宠物、退出和注销。
- 成员离线录入期间被移除，恢复联网后的结果明确且不越权。
- 活动最后一个名额、重复报名、本人取消、组织者改期和活动结束清理。
- 已发布内容修改、审核不通过、旧分享访问与下架后恢复。
- 游客打开文章、路线、静态健康摘要和私有档案相关链接，访问边界一致。
- 用同一份样例事件计算激活、提醒完成、导航发起和收藏回访，口径一致。

以上条件完成前，可继续不依赖未决规则的设计或基础工作；依赖这些规则的业务契约与验收结论应保持未关闭状态。本报告提出的建议经负责人复审后再回填定稿文件。
