## 0. 总目标与完成定义（DoD）⭐

**一句话目标**：一条命令在本地拉起全部端与服务，演示数据可点可用，需求范围内 100% 功能可测，全部验收用例通过、无 P0/P1 缺陷。

### 0.1 「本地可以测试」标准（可客观验证）

| # | 标准 |
|---|------|
| 1 | `pnpm install && pnpm dev` 后同时可访问：用户端 Web、官网、管理端、移动 H5、API（5 个本地地址，写入 README） |
| 2 | 内置 `pnpm seed` 演示数据：≥2 账号、≥3 宠物、30 篇文章、200 POI、50 商品、举报/投稿样例、1 个家庭组 |
| 3 | 手机验证码在 dev 模式固定（如 `123456`）或打印到控制台，无需真实短信/微信即可注册登录 |
| 4 | 数据库零配置（SQLite 文件），删库重建一键 `pnpm db:reset` |
| 5 | 每个里程碑合入后主分支可运行（不许出现「合不进去跑不起来」的中间态） |

### 0.2 「功能完善」标准

- 需求 `需求全景-功能清单.md` §5 **In Scope 全量**（A1–A5、B1–B6、C1–C7+C9、D1–D7、E1–E3、F 全部、H1–H2）逐条有对应实现 + 验收用例（见 §6 用例地图）。
- 四端 UI/UX 按已产出的设计文档实现（含动效、空态、异常态、合规页面）。
- Out-of-scope 项**确认不存在**（无购物车/订单/支付、无商业化、无青少年模式）。

### 0.3 「无 Bug」标准（退出准则，见 §5 详表）

P0（崩溃/资损/合规事故）= **0**；P1（主流程中断）= **0**；P2 ≤ 5 且全部登记挂账；Playwright E2E 全绿；两轮完整回归通过；四端手动矩阵无未决项。

## 1. 技术选型决议（阶段二 · 本表为决议草案，评审可推翻）

> 依据 AGENTS 约定：选型内容只写在 `docs/05-技术文档/`，不回流 docs/01、02。

| 层 | 选型 | 理由 / 备选 |
|----|------|-------------|
| 仓库 | **pnpm workspaces monorepo** | 四端共享类型与 UI 包；备选 turborepo（后期加缓存） |
| 前端框架 | **Vue 3 + TypeScript + Vite** | 国内生态成熟、四端同构成本低；备选 React 18 |
| 状态/路由 | Pinia + Vue Router | |
| 用户端 Web | 自定义组件（基于设计令牌） | 设计系统已定义，不重依赖 UI 库 |
| 管理端 | **Element Plus** | 表格/表单/权限组件现成，提效最大 |
| 移动端（一期形态） | **响应式 H5**（自适应 57 屏，移动浏览器/App WebView 均可测） | ⚠️ 决议：原生 App/小程序后置。**厂商推送留 service 接口**，本地用 Web Notification + 站内消息模拟 L2；需求层面功能全量不受影响 |
| 官网 | 同 Vue 栈，SSR 不做（一期 CSR + 预渲染 SEO 页） | 备选 Nuxt（若 SEO 验收不达标再升） |
| 后端 | **Node 20 + Fastify + Prisma + SQLite（本地）** | 零配置本地测；Prisma schema 直译自 `数据设计.md`；生产切 PostgreSQL 仅换 connector |
| 认证 | JWT（access+refresh）；dev 短信=固定码；**微信登录 dev stub** | 对齐需求 A1 |
| 提醒调度 | 本地 cron 进程（每分钟扫描） | 状态机见功能设计；推送=站内+Web Notification |
| 内容安全 | **本地词库机审 + 图片规则 stub**，`ModerationService` 接口预留厂商（阿里云内容安全等） | 满足「先审后发/疑似转人工」流程可测；生产接入属部署期 |
| 搜索 | 后端 LIKE/全文检索（SQLite FTS5） | 一期够用；ES 属二期 |
| 契约 | **OpenAPI 3 先行**：api 定义 zod/类型 → 生成 spec → 前端生成 client | 前后端并行的前提 |
| 测试 | **Vitest**（单测）+ **Playwright**（E2E）+ ESLint/Prettier/husky | |
| 数据 | Prisma migrate + seed 脚本 | §0.1-2 |

## 4. 执行顺序与并行策略

```
M0 基建+契约 ──┬─→ M1 后端账号 ─┬→ M2 管理 → M3 资讯 → M4 探索 → M5 用品 → M6 治理看板
（严格先行）   │                │        （后端可 2 人按域并行）
               ├─→ M7 Web（契约+mock 先行，接口就绪切真）
               ├─→ M8 管理端（依赖 T6.1 权限 + 各域 API）
               ├─→ M9 官网（只读内容，最早可完成）
               └─→ M10 H5（复用 M7 组件，后置 20% 工期）
                        ↓
              M11 质量工程（测试用例与开发同步写，不留到最后）
                        ↓
              M12 除虫 → 两轮回归 → 交付验收 ✅
```

- **契约先行**是并行前提：T0.4 完成前，前端只允许写静态页与组件。

## 5. Bug 治理与「无 Bug」退出准则

**分级**

| 级 | 定义 | 例 |
|----|------|-----|
| P0 | 崩溃/数据错误/合规事故/资金(未来) | 注销后仍可登录、他人档案越权可见、举报入口缺失 |
| P1 | 主流程中断、无绕过 | 无法建档、投稿卡死、审核操作失效 |
| P2 | 功能瑕疵有绕过 | 空态文案错位、排序不精确 |
| P3 | 观感 | 间距 1px、文案错别字 |

**流程**：复现录屏 → 入池定级 → 修复（附回归用例）→ QA 回归 → 关闭。P0/P1 当日修复；修复引入的新缺陷记为回归缺陷，责任随源任务。

**出口准则（全部满足才可宣称「无 Bug」）**

1. 缺陷池：P0 = 0、P1 = 0、P2 ≤ 5（全部登记进《已知问题清单》并给出计划）、P3 ≤ 15 或清零；
2. E2E（T11.2）连续两次运行 100% 通过；
3. 手动矩阵（T11.3）两轮 100% 通过，无未决项；
4. 核心域单测绿 + 覆盖率达标（T11.1）；
5. 14 天内无新增 P0/P1（观察窗，短周期项目可缩至 7 天，评审定）；
6. 合规自查（T11.5）通过 —— 法务文案未到位项按外部依赖挂账，不算缺陷。
