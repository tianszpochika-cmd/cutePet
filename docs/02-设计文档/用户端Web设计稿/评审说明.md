# cutePet 用户端 Web UI/UX 稿 · 评审说明

> 状态：设计评审稿 · 日期：2026-09-23
> 范围：养宠用户在桌面 Web 上的照护、阅读与协作体验。此稿用于确认页面结构和交互意图，不能代替开发完成或真实业务验收。

> 实现进展：本稿第 7 节保留设计评审时的实现快照；2026-09-23 的源码回填见文末第 9 节。

## 1. 设计依据与评审范围

本轮 Web 稿承接[官网设计稿](../官网设计稿/评审说明.md)的「照护有记录、下一次有安排、家人能协作」叙事，把访客已经理解的价值变成登录后的可执行任务。[用户端总览](index.html)可进入首次使用、照护和家庭三个交互预览；[全站页面蓝图](全站页面蓝图.md)列出当前路由的设计覆盖与待补页面。预览中的名字、宠物及记录均是**设计示意**。

信息和规则依据：[多端需求矩阵](../../01-需求文档/需求-多端需求矩阵.md)、[账号与家庭共享需求](../../01-需求文档/需求-账号与用户体系.md)、[宠物管理需求](../../01-需求文档/需求-宠物管理.md)、[业务规则 BR-02/03/04/07](../../01-需求文档/需求-业务规则与生命周期.md)、[Web 信息架构](../信息架构.md)和[闭环页面与状态](../功能设计-闭环页面与状态.md)。现有实现以 `apps/web/src/router.ts`、页面组件和领域规则为核对对象。需求文档仍处评审中；本稿不替需求方裁定未决事项。

## 2. 目标用户与首页任务

| 用户情境 | 想完成的任务 | 设计重点 |
|---|---|---|
| 首次养宠或刚开始使用的人 | 登录、为宠物建档、留第一条记录、安排下次提醒 | 首页任务入口清楚；向导保留进度；只在用户主动建档时进入向导 |
| 日常照护人 | 看谁处理了待办、录入健康/体重记录、查看下次安排 | 宠物与待办优先于资讯；提交结果与平台保存状态分开表示 |
| 多宠家庭 | 在宠物之间切换，核对成员权限与处理人 | 每只宠物展示所有者、共享状态和本人可执行的动作 |
| 家庭管理员或受邀成员 | 邀请、加入、确认可见范围、处理授权变化 | 邀请前告知共享内容；管理员身份与宠物所有权分开 |
| 长文阅读和创作者 | 阅读资讯、检索、投稿与管理稿件 | 保留 Web 的宽屏阅读与编辑优势；来源任务登录后回跳 |

这些是根据需求整理的任务场景，不是已完成用户访谈或可量化的画像。用户端 Web 覆盖一期 C 端功能；桌面场景特别适合批量录入、查看体重曲线、打印健康摘要、长文创作和大屏探索。移动端的真实离站推送另有运行依赖，Web 页面不可把站内待办说成系统推送已送达。

## 3. 视觉系统与信息架构

**与官网统一的视觉基线**：奶油底色 `#FFF9F3`、深墨正文 `#2B2118`、暖橘强调与圆角卡片。原品牌橘 `#FF7A2F`用于插画和轻量装饰；白字主按钮用深橘 `#B85111`，这是官网稿为普通文本对比度提出的待统一令牌。管理、资讯、探索、用品使用各自浅色模块底，不能只靠颜色传达状态。`cutePet` 与爪印仍是工作名和占位标识。

**Web 与官网的职责**：官网说明产品并引导进入实际可用的端入口；用户端提供真实账号、宠物和任务操作。二者可共用品牌、颜色、字体和图形语言，用户端的导航、卡片密度和操作层级按桌面使用调整。正式接入前必须核对官网 CTA 地址、用户端路由、登录回跳和权限。

```text
用户端 Web
├─ 首页：本次待办、我的宠物、最近记录、次级资讯/探索/用品入口
├─ 宠物：列表与切换 → 建档向导 → 详情
│  ├─ 时间线 / 健康记录 / 体重曲线 / 提醒计划与待办
│  └─ 健康摘要（仅所有者核验导出）/ 分享设置 / 归档与回收站
├─ 资讯：频道 / 搜索 / 文章；创作中心与投稿状态
├─ 探索：场所 / 路线 / 活动；用品：商品资料 / 评测 / 清单
└─ 我的：家庭 / 消息 / 收藏 / 活动中心 / 设置、隐私、帮助
```

桌面全局导航沿用[信息架构](../信息架构.md)的「首页｜宠物管理｜资讯｜探索｜用品」，家庭、消息和个人中心在右侧。首页主区先显示可执行的照护任务，再放内容发现；没有待办时用平静的完成或空态，不制造紧急感。公开内容允许游客阅读；建档、记录、互动、报名和家庭操作按登录及权限流程执行。

## 4. 核心任务流及提交边界

| 任务 | 入口与主要步骤 | 必须显示的结果与异常 |
|---|---|---|
| 登录与回跳 | 游客在原页面发起写操作 → 登录/注册 → 首次协议勾选、实际年龄分支、必要时监护人同意 → 返回原对象与确认位置 | 原输入和来源任务应保留；加入、发布、报名、删除等在登录后**重新确认**，不得自动提交；拒绝或失败有可恢复入口 |
| 建档 | 首页/宠物列表 → 主动选择新建 → 向导填写基本资料 → 预览并保存 → 宠物详情 | 中断可继续完善；未登录先进入登录闸门；平台保存成功前不能展示“已建档” |
| 记录 | 宠物详情 → 选体重或健康记录 → 填发生日期与类型字段 → 检查关联计划 → 保存 → 时间线与曲线/摘要更新 | 保存失败保留输入并给重试；仅体重更新体重曲线；离线草稿明确“尚未保存到平台”，失权草稿不得上传 |
| 提醒 | 宠物详情/首页待办 → 查看计划与本次待办 → 选择已有记录或新增记录 → 确认完成 → 查看处理人和下一次安排 | 计划与待办状态分开；健康类待办须绑定有效记录；家人已处理时展示统一结果，不重复完成；无实际推送渠道写“仅站内提醒” |
| 家庭 | 家庭页 → 明确家庭管理员与各宠物所有者 → 宠物所有者主动共享 → 管理员邀请并先告知范围 → 受邀人核对家庭与默认只读 → 确认加入 | 未共享宠物仍私有；家庭管理员不继承他人宠物管理权；被撤销权限后停止访问。宠物所有权转移与管理员转交为独立、双方核验流程 |

健康摘要是经**宠物所有者核验**生成的静态快照，显示生成时间、选择的时间窗和缺项；它不能成为实时私有档案的公开链接。对不具备权限的深链，应先拒绝再渲染，不显示私有标题、照片或内容。

## 5. 家庭协作页面的权限规格

家庭角色和宠物角色分开：一个家庭只有一个家庭管理员，但每只宠物都有自己的唯一所有者。共享档位按「成员 × 宠物」设置，新成员对已共享宠物默认只读；个人宠物不会因为加入家庭自动开放。非所有者只能看见**自己**对某只宠物的档位，不能查看其他成员的授权表。邀请告知应列出可能可见的档案、健康记录、时间线、提醒和录入人；收藏、草稿、私人联系方式、报名信息不自动共享。

| 动作 | 宠物所有者 | 该宠物可管理成员 | 该宠物只读成员 | 仅家庭管理员身份 |
|---|:---:|:---:|:---:|:---:|
| 查看已共享档案、健康和时间线 | 是 | 是 | 是 | 无额外权限 |
| 编辑普通字段、新增健康记录 | 是 | 是 | 否 | 无额外权限 |
| 更正或删除健康记录 | 任意条目，留痕 | 仅本人录入且当前仍有权限 | 否 | 无额外权限 |
| 创建/编辑提醒计划、完成或跳过待办 | 是 | 是 | 否 | 无额外权限 |
| 导出摘要或完整宠物数据 | 核验后 | 否 | 否 | 无额外权限 |
| 设置共享、归档/删除/恢复/转移宠物 | 是 | 否 | 否 | 无额外权限 |
| 邀请/移除家庭成员、转交管理员、解散家庭 | 同时是家庭管理员时 | 同左 | 同左 | 是 |

预览提供「宠物所有者」「可管理成员」「只读成员」视角切换，只显示当前视角能看到的宠物和写操作；未共享宠物对非所有者不展示姓名或记录。邀请在告知确认之后才进入下一步设计示意。宠物所有权转移、家庭管理员转交只讲影响和要求，预览不模拟提交或成功。

## 6. 页面状态、响应式与无障碍

| 状态 | 设计要求 |
|---|---|
| 加载 | 宠物、待办、家庭授权等使用与布局匹配的骨架；保留页面标题和返回路径 |
| 首次空态 | 无宠物引导主动建档；无记录引导记录第一条；无家庭引导创建/加入；无待办明确当前没有待处理事项 |
| 错误与弱网 | 解释失败动作，保留用户输入，提供重试；待同步草稿与平台已保存记录在视觉和文案上分开 |
| 无权限/已失效 | 不先渲染私有数据；说明授权已变更、对象已归档/删除或邀请已过期，并提供安全返回入口 |
| 并发冲突 | 展示当前值与本次修改，允许放弃或再次确认覆盖；家人已处理待办时刷新为平台最新结果 |
| 异步成功 | 只有平台确认后才展示成功和新的状态；通知创建、渠道接受、可确认送达与打开不得混成一个“已送达” |

桌面采用最大宽度内容区、宠物列表与详情双栏及表单旁的辅助说明；窄屏改为单列，重要行动保留在任务附近，权限矩阵允许有标签的横向浏览，避免整页横向滚动。评审至少看 375px、768px、常见桌面宽度、200% 字号/缩放和长内容。触控目标不小于 44×44，Web 鼠标目标不小于 40×40；正文对比度按 WCAG AA 4.5:1。键盘顺序跟视觉顺序，所有控件有可见焦点，错误与异步反馈供辅助技术读取；系统选择减少动画时停止循环和位移动画，内容始终可读。

## 7. 当前实现与验收边界

`apps/web/src/router.ts` 已列出首页、认证、宠物、提醒、家庭、创作、探索等路由及 X01–X16 的部分页面。路由存在、页面有交互或领域单测通过，都不等于端到端的业务流程、跨端数据、真实推送或正式发布已验收。当前家庭页 `FamilyPage.vue` 的成员明细仍是空列表骨架；`ShareManage.vue` 使用本地示例授权数据；转移页也需按真实接口和双方核验流程验证。评审时应把这里当成**目标设计与实现差距**，不能写成已完成能力。

编写本设计稿时，首页 `Home.vue` 使用本地会话演示态，`TodoConfirm.vue` 的提交为模拟结果，`ReminderCenter.vue` 从列表直接触发提醒完成，`ExploreMap.vue` 为地图占位。后续源码回填已移除部分假结果，但仍要按本稿的登录、关联记录、处理冲突和真实数据边界继续核对。[状态表](../../05-技术文档/状态表.md)所称 M7「开发完成」指此前代码与纯逻辑测试；[双端验收与 LE 未完成清单](../../07-交付/双端验收与LE未完成清单.md)的 E01–E10 及用户链走查仍未完成。

编写本稿时还发现：`apps/web/src/domain/family.ts` 的 `petActionAllowed` 在非所有者编辑/提醒判断中，对 `MEMBER` 家庭角色直接返回 `false`；这与 BR-03「该宠物可管理成员可编辑/处理提醒」的逐宠物授权规则不一致。本轮源码已避免把家庭角色当成逐宠物授权证据；正式落地仍须服务端逐对象权限回执和跨账号验证，不能让 UI 仅隐藏按钮来承担访问控制。

本轮静态 HTML 是体验预览，不连接登录、家庭、记录、提醒或通知服务；示例姓名、宠物、日期和权限变动不代表用户真实数据或平台保存成功。后续真实验收需要分别验证页面、服务端授权、跨账号/跨端同步、撤权后的深链和缓存、并发待办、失效邀请及转移回退。

## 8. 待定决策与评审问题

| 待确认事项 | 所需决定或证据 |
|---|---|
| 品牌名、标识和端间组件令牌 | 负责人确认正式品牌资产及深橘主按钮令牌，统一官网与 Web |
| 官网进入 Web 的正式地址 | 核对域名、登录回跳、来源任务和不可用状态 |
| 家庭成员明细及共享设置接口 | 明确按宠物返回的所有者、本人档位、可见范围、授权版本和错误码；验证撤权时私有数据不泄漏 |
| 可管理成员的权限实现 | 对齐 BR-03 与当前 `petActionAllowed` 的冲突，确认服务端同口径执行 |
| 家庭邀请与转移的真实流程 | 核对邀请码 7 天有效、邀请前告知、双方核验、24 小时待接受、撤销/过期和通知结果 |
| 照护记录与提醒的结果反馈 | 用跨成员、跨端和弱网实测验证平台保存、重复处理和下一期排期 |
| 最终页面稿取舍 | 评审首页内容密度、宽屏双栏、窄屏权限表和提示文案后，再固化组件 |

评审时重点问三件事：用户能否从首页完成一次「建档 → 记录 → 安排下一次」；家人切换视角时是否准确理解「我能看什么、能做什么」；每个成功、失败、无权限和待同步状态是否与平台真实结果一致。

## 9. 2026-09-23 实现回填

用户端 Web 已按本稿整理照护优先首页、登录回跳、宠物档案与记录、资讯、探索、用品、家庭和设置页面。页面分别呈现加载、无数据、失败及待接入状态；对缺少真实回执的完成、共享、注销等动作不再给出本地成功。请求统一走同源 `/api`，路径参数已与现有客户端兼容。

当前登录默认关闭，真实短信、正式协议、网关可信身份转换、逐宠物授权和待办原子完成仍未接通。质量退修文案已按 BR-06 修正，但内容服务仍有相反规则，登记为 F03。上述代码只完成静态逻辑审核，未运行构建、浏览器或服务；详见[四端前端实现与静态审核](../../07-交付/四端前端UIUX实现与静态审核-2026-09-23.md)。
