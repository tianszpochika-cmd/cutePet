## 1. 交付范围

## 2. 体验目标与页面层级

内部运营的主要任务是准确判断并能复核结果。工作台先给出超时、投诉、失败通知和清理待办，再提供相应业务域入口。列表显示对象、状态、等待时长和负责人；详情核对当前版本、证据范围、历史处理和动作影响。一级页面与现有管理端路由对应：

| 页面组 | 当前路由 |
|---|---|
| 登录 | /login |
| 总览与运行异常 | /dashboard、/todos |
| 内容审核与运营 | /review、/content |
| 商品与探索 | /products、/explore、/credentials |
| 用户治理 | /governance |
| 系统管理 | /audit、/roles |

管理端一期仅面向桌面 Web。设计稿在窄视口提示“请在电脑端使用”，没有把多列表格压成移动管理页。正式实现应按明确的浏览器和窗口范围验证布局、键盘效率及 200% 缩放。

## 3. 权限与核心任务链

侧边栏按当前账号权限点隐藏无权入口，业务域卡片和待办也按授权范围返回。隐藏入口不承担鉴权：打开深链、查询列表、读取证据和提交动作都要由服务端校验权限点、对象归属、工单范围与当前版本。治理人员查看私人健康证据只允许在工单绑定的最小范围内，并记录用途；普通运营列表不展示宠物健康档案。

既有规则保留 32 个权限点和 6 个预置角色。本稿在总览提供管理员、审核员、POI 运营三个视角，用于评审导航和信息密度；它不是完整的权限分配工具。用户封禁、角色权限管理和系统设置等高危能力要同时满足授权、二次确认和审计。管理员预置角色不可编辑或删除。

| 任务 | 入口与判断步骤 | 必须有的结果与异常 |
|---|---|---|
| 登录及回到任务 | 内部入口 → 账号/密码 → 服务端核验身份与权限 → 回到允许的原任务 | 凭据错误不暴露账号是否存在；无后台权限先拒绝；会话过期保留非敏感上下文，高危动作重新确认 |
| 投稿审核 | 按 SLA/风险排序 → 认领 → 核对当前提交版本、来源与历史 → 通过或附意见驳回 | 驳回必填意见；修改稿仅当前版本被审；他人已认领或状态变化时阻止旧操作；结果以平台确认和审计为准 |
| 举报与内容安全 | 疑似内容/举报/版权通知 → 看对象与证据 → 人工复核 → 通知及申诉入口 | 机审“疑似”不直接处罚；普通举报与版权通知的时限和动作分开；失败通知进入待办 |
| 供给运营 | 内容、商品、POI、活动、机构列表 → 看来源与影响 → 填原因/核验 → 提交 | 商品只做内容导购；POI 纠错先对照现值；领养始终人工审核；活动重大变更跟踪报名暂停、通知和清理 |
| 用户治理 | 脱敏搜索 → 最小必要详情 → 选独立处罚动作 → 二次确认 | 说明原因、期限和影响；失败不改变状态；受限账号仍可申诉和查询 |
| 异常与审计 | 失败通知/清理/复核 → 负责人核查 → 真实结果确认 → 逾期升级；审计按区间查询 | “后台任务已运行”不等于已送达或已清理；审计包含操作者、时间、IP、对象、动作与脱敏前后摘要 |

批量操作只允许适用对象和同类状态，先展示数量、范围、不可撤回影响及意见，再二次确认。成功、失败和部分成功分别显示，不能用一条成功提示掩盖未处理项。

## 4. 页面状态与可用性

| 状态 | 设计要求 |
|---|---|
| 加载与空 | 保留标题、筛选和返回路径；列表骨架对齐列宽；无待办与无权限域分别说明 |
| 错误与弱网 | 保留筛选、意见和对象上下文；提交中禁用重复动作；超时先查平台结果再重试 |
| 无权限与失效 | 深链先拒绝，不闪现管理数据；说明授权变化、对象下架或他人已处理 |
| 并发与版本 | 显示当前状态与本次输入差异；不沿用旧页面提交已认领/已处理对象 |
| 审计与敏感信息 | 默认脱敏；私有证据按工单最小范围读取；高危操作的原因和确认结果可追踪 |
| 指标与 SLA | 显示分子、分母、观察窗和数据成熟状态；零分母为“—”；24 小时超时与 48 小时升级用颜色加文案表达 |

管理端点击目标不小于 40×40，焦点可见；列表、筛选、弹窗和确认可用键盘完成。弹窗关闭后焦点返回触发点；错误和异步结果供辅助技术读取。减少动画设置下不依赖位移表达状态。

## 5. 当前实现与验收边界

管理端已有登录、工作台、审核、内容、商品、探索、用户治理、审计和角色的路由及页面骨架。编写本稿时，AdminLogin.vue 以本地输入规则和开发角色预览进入工作台；AdminLayout.vue 默认以全部权限渲染导航。Dashboard.vue 的指标、OpsTodos.vue 的待办和 AuditLogs.vue 的记录都来自本地示意数据。ReviewWorkbench.vue 使用本地队列和本地状态变化演示认领、审核、批量处理，不能当作跨人锁、真实发布或审计成功证据。

进一步核对发现：审核页的队列 Tab 尚未按类型与权限真实筛选，单件审核没有强制先领取，批量通过没有真实二次确认；用户治理页只有硬编码示例，角色页未实现高危权限保存的二次确认。内容、商品、探索和资质页多使用本地列表与消息；探索纠错的合并字段和处理过滤字段不一致，活动变更的逐人通知失败待办、商品治理清除传播结果、资质材料的最小范围查看仍待验证。另有一处规则冲突：业务规则 BR-06 明确“质量退修不暂停投稿”，但当时 `apps/admin/src/domain/governance.ts` 在质量退修次数达到 3 次时仍返回 `suspended: true`；本轮前端规则已修正，内容服务仍需单独修复。上述差距是编写本稿时的快照，不能当作本轮代码已完成真实业务流程的证据。

这些现状只说明页面与部分交互逻辑存在。真实登录、服务端权限、内容版本审核、处罚、运营数据、失败通知/清理、审计完整性及跨账号并发仍需运行证据。[状态表](../../05-技术文档/状态表.md)中的“开发完成”与[双端验收及 LE 未完成清单](../../07-交付/双端验收与LE未完成清单.md)的运行/业务验收要分别报告。设计稿中的姓名、队列、数字和结果均为示意，无平台写入。

## 6. 下一轮评审问题

1. 审核员能否从超时队列进入当前版本，明确认领、理由、影响与最终审计结果？
2. 多人并发、权限变化或平台返回失败时，能否停在可恢复且不误报成功的状态？
3. POI 运营、审核员和管理员切换时，导航、列表、证据范围与操作是否同步收敛？
4. 指标是否有分子分母、观察窗与“暂无可用数据”的表达？失败通知和清理是否有可追踪的人工作业出口？
5. 哪些现有路由需独立细页，哪些可在工作台内用抽屉或 Tab 承载？正式品牌、登录服务和审核人力排班由负责人确认。

## 7. 2026-09-23 实现回填

管理端源码已将演示登录改为仅内存的只读界面预览；侧栏、工作台、审核样例、公开内容与供给读取、治理和审计页面均明确标出身份及数据边界。示例审核仅供核对筛选、认领、版本和理由交互，不发出管理写入；看板不再显示虚构指标。

管理员真实登录、权限、审核锁、操作回执与审计仍由服务端提供。桌面布局和窄屏提示只经源码检查，尚未运行构建、浏览器或真实管理账号流程；详见[四端前端实现与静态审核](../../07-交付/四端前端UIUX实现与静态审核-2026-09-23.md)。
